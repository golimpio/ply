## M1 BLOCKING: burned-in bitmap subtitles are never scaled to the video
- **Where:** `internal/hwaccel/plan.go:262` (`burnGraph`):
  `scale2ref=w=main_w:h=main_h`.
- **Defect:** in `scale2ref`, `main_w` and `main_h` are the size of the input being scaled
  (the subtitle canvas), so the scale does nothing.
- **Verified with ffmpeg 9.0.2,** scaling a 320x180 canvas against a 640x360 video:

  | Expression | Output size |
  |---|---|
  | `scale2ref=w=main_w:h=main_h` | 320x180 (unchanged) |
  | `scale2ref=w=iw:h=ih` | 640x360 |
  | `[sub][ref]scale=w=rw:h=rh` | 640x360 |

  ffmpeg also warns "scale2ref is deprecated, use scale=rw:rh instead".
- **Effect:** PGS or VobSub burn-in on any video whose size differs from the subtitle canvas
  (for example 4K video with a 1080p PGS, the browser profile having no resize) draws the
  subtitles at canvas size in the top-left corner. The reviewer reproduced this end to end
  (box at x110..209 instead of x220..419).
- **Fix:** use the non-deprecated two-input `scale=w=rw:h=rh`, with the video split so it
  can serve as the reference, or `scale2ref=w=iw:h=ih`.
- **Tests:**
  - `plan_test.go:170` pins the buggy string; update it.
  - The existing burn-in tests (`TestImageSubtitleIsBurnedIn`, `TestBurnInGraphRuns`) use a
    canvas the same size as the video, so they can't tell a no-op scale from a correct one.
    Add a mismatched-canvas integration case (640x360 video with a 320x180 `.idx`) that
    asserts the overlay's position or size.

## M2 SHOULD: libx264 transcode of an odd-dimension source returns 500
- **Reproduced** (the reviewer's server-level test, re-run by rare-tiger): an 853x479 ffv1
  mkv transcoded with libx264 gives init.mp4 status 500 `{"error":"internal error"}`. The
  same file on `h264_videotoolbox` returns 200.
- **Root cause not pinned yet:** plain `ffmpeg … -vf format=yuv420p -c:v libx264` encodes
  853x479 and 642x361 with exit 0 on this ffmpeg, so it is not simply "libx264 rejects odd
  sizes". Something in the server's libx264 arguments breaks (profile, level,
  `-force_key_frames` and HLS fmp4, or a scale step).
- **Fix:** read the actual ffmpeg stderr for this case first, and log it. That 500 hides the
  ffmpeg error from the user and the log, which is a defect in itself. Then force even
  output dimensions in the software chain (`scale=trunc(iw/2)*2:trunc(ih/2)*2` when
  needed), and round `MaxHeight` down to even in `target` (a custom profile can send
  `maxHeight: 361`).
- **Test:** an odd-dimension source on the libx264 path, plus an odd custom `maxHeight`.

## M3 SHOULD: subtitle conversions outlive server shutdown
- **Where:** `internal/subs/subs.go:141`.
- **Defect:** `go g.fill(context.WithoutCancel(ctx), …)`, with a 10-minute timeout and
  ffmpeg in its own process group. `cmd/ply/main.go` never stops `subGen` at shutdown.
- **Effect:** SIGTERM during the first extraction of a large file leaves up to 2 niced
  ffmpeg processes reading for up to 10 minutes, plus `<data>/subs/*.tmp` leftovers. That
  breaks "shutdown kills every child".
- **Fix:** give `subs.Generator` a base context or a `Close()` that cancels in-flight runs.
  Call it from main's shutdown path next to `streams.Close()`.
- **Test:** start a long extraction, call Close, and assert the process group is gone and no
  `.tmp` file remains.

## M4 SHOULD: transient subtitle failures are remembered until the file changes
- **Where:** `internal/subs/subs.go:200` (every non-context ffmpeg exit becomes `ErrConvert`)
  and `:161` (stored in `g.failed` until the cache name stops being live, i.e. the mtime
  changes).
- **Effect:** if the share is unmounted or asleep, or the disk is full, at first request,
  every later request returns 422 until restart, even after the drive comes back.
- **Fix:** don't remember a failure when `os.Stat(src.Input)` fails or the error looks like
  I/O. Alternatively, expire remembered failures after a few minutes.
- **Test:** fail once with the input missing, restore it, and expect success.

## M5 SHOULD: a track switch can save position 0 and erase the resume point
- **Where:** `web/src/components/Player.svelte:198` (`playback = undefined` in `restart()`)
  and `:138-139` (the `armed` gate in `ontimeupdate`).
- **Defect:** after `release()`, `el.load()` fires `timeupdate` at 0 (the event order was
  checked in Chromium by the reviewer). With `playback` undefined, `at` is 0, so
  `currentTime >= at - 3` re-arms the gate at position 0.
- **Effect:** any `report()` before the new stream seeks (pause, tab hidden, page hide, or
  the 10 s tick on a slow start) sends `positionSec: 0`. The server deletes progress below
  30 s, so the resume point at, say, 45:00 is lost after switching audio track or picking a
  bitmap subtitle.
- **Fix:** gate on a target position kept outside `playback` (the existing `resumeFrom`
  variable), and arm only once `currentTime >= resumeFrom - 3`.
- **Test:** best covered by the planned web unit tests, or extract the gate into a pure
  function and table-test it.

## Fixes

Each fix has a test that failed before it (run against a mutant that restores the old behaviour).
Not committed.

- **M1 fixed.** `burnGraph` no longer scales the canvas by itself. When this ffmpeg's `scale` takes a reference input (`hwaccel.Detect` records it as `Filters["scale:ref"]`, by the "dynamic" input in `ffmpeg -h filter=scale`), the graph is `[0:1]scale…,split=2[ref][vref];[0:3][vref]scale=w=rw:h=rh[sub];[ref][sub]overlay…`; otherwise `scale2ref=w=iw:h=ih` (in `scale2ref`, `iw:ih` are the reference's size and `main_w:main_h` the canvas's own). `plan_test.go` now pins both forms (`TestPlanBurnIn`, `TestBurnGraphScalesTheSubtitleToTheVideo`, `TestDetectNotesTheTwoInputScale`). New integration test `TestImageSubtitleIsScaledToTheVideo`: a 640x360 video with a real VobSub whose `.idx` says 320x180; the box must be white where the scaled canvas puts it (x 240-399, y 290-309: about 48 frames) and not where an unscaled one would (x 120-199, y 145-154), checked for both graph forms, with a clean-picture control for both places. With the old strings the test reports 0 frames in the right place and 48 in the wrong one. `docs/NOTES.md` burn-in sentence updated.
- **M2 fixed, root cause differs from the report.** libx264 rejects any odd width or height for 4:2:0 ("width not divisible by 2 (853x479)"); a plain `-vf format=yuv420p` encode of a true 853x479 source fails too (the reviewer's lavfi `testsrc2` silently produced 852x478, which is why it appeared to work). Two ways in: an odd source that is not resized, and an odd `maxHeight` (361 gave 642x361). The software chain now trims an odd source to even (`scale=trunc(iw/2)*2:trunc(ih/2)*2`), `target` rounds `MaxHeight` down to even (minimum 2), and the unknown-size form uses `trunc(min(ih,N)/2)*2`. Logging: the 500 already carried ffmpeg's stderr in the `request failed` line; the `ffmpeg stopped` line did not, so an ffmpeg that dies by itself now also logs `ffmpeg failed` with its stderr (not for one the server stopped). Tests: `plan_test.go` cases for odd source, odd width, odd limit, unknown size; `TestTarget`; `TestFFmpegFailureIsLoggedWithItsStderr` (with a control that a server-initiated stop is not logged as a failure); integration `TestOddDimensionsTranscode` (true 853x479 ffv1 source, both a plain and a 361 limit, libx264 and VideoToolbox). Fails with `height not divisible by 2 (642x361)` on the old code.
- **M3 fixed.** `subs.Generator` has a base context and a `Close()`: it cancels the conversions (the process group is killed, the `.tmp` removed), waits for them, and `Path` returns `ErrClosed` afterwards; a cancelled conversion is not remembered as a failure. `cmd/ply/main.go` calls `subGen.Close()` right after `streams.Close()`. Test: `TestCloseStopsConversionsInProgress` (a script that writes the output file, has a helper process and sleeps: both processes gone, no `.tmp`, the waiting request released, `Path` after Close refused). With a `Close` that does nothing it fails after 10 s.
- **M4 fixed, both ways.** A failed conversion is not remembered when `os.Stat(input)` fails afterwards (share asleep or unmounted), and a remembered one expires after 5 minutes (covers a full disk). Tests: `TestFailureOfAnUnreachableInputIsNotRemembered` (fail once with the input missing, bring it back, success), `TestRememberedFailureExpires`; `TestFailureIsRememberedUntilTheFileChanges` now uses a real input file.
- **M5 fixed together with S5 and W1 to W4, in `Player.svelte`.** The arming gate is now part of one state machine (`web/src/lib/progress.ts`, `Progress`; see `2026-11-02-review-art-web.md`): a stream's position counts only once the element has `readyState >= 1`, a `currentSrc`, is not seeking and is within 3 s of the position the stream was asked to start at (kept outside the cleared `playback`), and what the next stream starts from is kept in the tracker, so the `timeupdate` at 0 fired by `el.load()` can neither arm the gate nor overwrite the resume position. Vitest table test `web/src/lib/progress.test.ts` (`npm test`): a reload at 0 while resuming at 45:00 must not arm. Checked in Chrome (session restart, errors, Retry, bfcache restore): no `PUT` with `positionSec: 0` in any of them.
- **Test gaps:** not touched (the web test runner is another agent's).
